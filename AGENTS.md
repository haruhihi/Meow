# Agent Instructions

- Do not run `npm run build` by default. Prefer narrower checks such as `npm run lint`, `npm run p -- validate`, targeted type/diagnostic checks, or behavior-specific commands. Run `npm run build` only when explicitly requested or when a broad production-build validation is necessary before finishing a risky change.
- When the user says `push`, run `npm run build` until it passes, then create a git commit, then run `git push`.
- This dev container does not have `rg` installed. Use VS Code search tools or shell `grep` for text/diff searches instead of `rg`.
- When starting a development server, always stop the server and free the port before finishing the turn unless the user explicitly asks to keep it running.
- For mobile-facing pages, prefer components from the existing UI library over native/desktop-style controls, and design interactions for convenient touch use and browsing.
- In simulated app/PWA pages, top app headers and `NavBar` chrome should stick to the top while scrolling unless the page is intentionally full-screen or immersive.
- App UI theme colors must strictly follow the single shared public style source in `src/app/globals.css`. Prefer existing CSS variables such as `--meow-primary`, `--meow-accent`, `--meow-warm`, surface, text, and gradient tokens instead of repeated local hex/rgba colors; add a semantic token in `src/app/globals.css` before introducing a reusable UI chrome color. Do not treat `src/styles/theme.ts` as a second app theme source; it may only reference shared CSS variable names or hold non-UI business/category/chart palettes when those colors encode data categories.
- For mobile/PWA list-detail flows, prefer natural document scrolling and cache-first rendering over manual scroll restoration. Avoid global `html`/`body` scroll locks unless the page is intentionally full-screen; fixed top/bottom UI must account for Android dynamic viewport behavior and iOS `env(safe-area-inset-*)` safe areas. Persistent bottom UI such as TabBar, bottom action bars, and fixed icon buttons must reserve `env(safe-area-inset-bottom)` so iOS home indicator/system gestures never cover icons or labels; verify this on mobile after touching app shell or fixed bottom UI.
- For app pages with previously loaded data, default to stale-first rendering: show existing store data immediately, keep it visible during refresh/update, and use pull-to-refresh or explicit refresh actions instead of clearing the screen into a loading state. In the Stocks chain specifically, returning to list/detail/report/financial pages must not auto background-refresh cached MobX data on mount; refresh only when the user pulls to refresh, taps an explicit refresh action, or a mutation flow deliberately calls `reQuery`/refresh after saving. Use SPA navigation for internal Stocks/report links to preserve the MobX store across back navigation; use `next/link` with `prefetch={false}` when avoiding automatic route prefetch, and avoid plain internal `<a>` document navigations unless intentionally discarding store state. When there is no existing data yet, render a centered loading placeholder first, then render the data; do not show empty, not-found, fake default, or other transient placeholder states while the request is still unresolved. If the page has a persistent header card, place the centered loading placeholder below that card.
- For icon + text buttons on mobile, always wrap the contents in a dedicated inline-flex `white-space: nowrap` element/class and make the button `flex-shrink: 0` when placed beside titles or toolbar text. Avoid broad selectors like `.header span` that can style nested button labels.
- Follow KISS: prefer reusing existing code, components, calculation utilities, validation helpers, and formatting functions before adding new ones. Keep the simplest existing path that satisfies the requirement; add abstractions only when they remove real duplication or prevent calculation, input, or persistence behavior from drifting.

## Stock financial analysis workflow

- Stock data must follow a three-layer boundary:
	- Layer 1 raw persistent data: store Tushare/user facts as directly as practical, with no business calculations. Examples: `StockFinancialStatement` raw `income`/`balance`/`cash_flow` JSON rows, dividend event terms, user holdings/cash/markings/overrides, and current quote price.
	- Layer 2 derived cache data: store expensive calculations only with explicit freshness metadata. Cache rows must identify the source boundary such as `calculatedThroughReportDate`/`calculatedThroughReportName`, `calculatedThroughSnapshotDate`, `calculationVersion`, `calculatedAt`, `status`, and warnings. New financial statements or valuation snapshots must make older affected cache stale and require refresh.
	- Layer 3 real-time data: use current price plus Layer 2 cache/source facts for current market cap, current PE TTM, current dividend yield, current holding market value, and other live price-derived metrics.
- Do not treat cached values as source facts. UI/report output should surface the cache freshness boundary, such as `财务数据截至 2025年报` or `估值分位截至 2026/05/29 周频快照`, and show warnings for missing source inputs instead of substituting a different accounting concept.
- Core data boundary: only stock price is treated as live-changing quote data. Fundamentals, total shares/share capital, dividends, financial statements, and non-price valuation inputs must come from persisted DB rows synced from Tushare on schedule or by explicit manual sync.
- Stock calculations should be rigorous rather than convenient: do not invent or substitute financially meaningful source inputs. If a required Tushare/user source field is missing, return `null`, mark the cache/status/warning, or show a missing-data warning instead of using nearby dates, latest available shares, current shares, vendor defaults, or another accounting concept as a silent fallback. UI placeholder fallbacks are fine; valuation, dividend, share-count, market-cap, and report calculations are not.
- Dividend yield must be based only on user-marked normal dividend events (`StockDividendMarking.countTowardNormalizedDividend`) or an explicit `StockMetricOverride.normalizedDividend`. Do not infer normalized dividend yield from unmarked/latest dividend events.
- Historical dividend yield must use a strict rolling TTM cash-dividend basis: include only implemented/paid dividend events whose `exDividendDate` falls in the trailing 12-month window, compute cash amount from Tushare `cashPerTen` and `dividendBaseShares`, and divide only by Tushare `StockValuationSnapshot.totalMarketCap` for that week. Do not use marked normal dividends, current normalized dividends, latest/current total shares, nearby share counts, `close * shares`, or Tushare/vendor dividend-yield fields as substitutes for this chart.
- Dividend cash calculations require Tushare dividend base fields. Use `StockDividendEvent.dividendBaseShares` and preserve `dividendBaseDate` for auditability; if the base is missing, do not estimate it from split/bonus/transfer terms or valuation snapshots except in one-off diagnostic scripts explicitly labeled as estimates.
- Use current price from the quote interface plus persisted Tushare total shares to derive market cap for valuation. Do not persist or refresh vendor market cap in `StockQuote` as a live quote field.
- Before relying on a total-shares/share-capital field, verify the Tushare mapping/API. Prefer `daily_basic.total_mv` for historical market cap and `balancesheet.total_share` for report-date share capital.
- Do not sync Tushare financial statements before every report. GitHub Actions refreshes financials with `--skip-current`, so it should only do the full Tushare statement fetch for symbols whose latest remote report period is newer than the persisted local report period. Default to the persisted DB data unless the user asks to refresh or required rows are missing.
- Only run a manual sync when the user explicitly asks to refresh, when required statements/dividends are missing/stale, or when investigating a suspected data issue. Source data refresh must use the full Layer 1 + Layer 2 workflow: `npm run sync:stock-source-data -- --symbols <symbol> --replace-source --sleep 0` for selected stocks, or omit `--symbols` for the stock universe. This first syncs Tushare dividend events, then financial statements, then refreshes `StockMetricCache` for the same scope. Use `--dry-run` only for checking the Tushare sync; dry runs intentionally skip cache refresh.
- When adding a stock to `src/config/stock-universe.json`, sync source data with `npm run sync:stock-source-data -- --symbols <symbol> --replace-source --sleep 0`, then valuation snapshots/cache and current quote. Financial statements and dividend events should not be refreshed through separate manual workflows.
- After syncing valuation market snapshots with `npm run sync:stock-valuations`, refresh Layer 2 valuation caches with `npm run refresh:stock-metric-cache` for the affected symbols or full universe so PE/PB percentile caches expose the latest `calculatedThroughSnapshotDate`.
- `StockFundamental` stores the compact metrics used by the stock page. `StockFinancialStatement` stores raw Tushare `income`, `balance`, and `cash_flow` rows keyed by `symbol + statement + reportDate`; prefer this raw table for report generation and field verification.
- Tushare field mappings live in `src/config/tushare-financial-fields.ts`. Do not rely on guessed labels; verify new fields against Tushare API responses before using them in analysis.
- Generate reports as Markdown and save them to `StockAiReport` with stable slugs using the local DB path; the app does not call an online LLM. Reports should appear on the global AI report page and in each stock's `洞察` page.
- Report generation should use: persisted three-statement data, current quote/market cap, user-marked dividend events, existing holdings, and framework cards from `src/config/stock-ai-framework-cards.ts`.
- For each analysis, separate evidence from judgment: cash conversion, free-cash-flow dividend coverage, balance sheet quality, channel/prepayment strength, valuation via `P = PE * E`, portfolio sizing/rebalancing, and conditions that would change the conclusion.
